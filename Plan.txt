# Project Prompt: Microcontroller AI Lab — AI-Powered Interactive Electronics Learning Platform

## 1. Project Overview

Build a complete, working full-stack web application called **Microcontroller AI Lab**.

The application is an interactive educational platform that helps beginners learn microcontrollers, electronics, circuit connections, embedded programming and basic hardware simulation through a guided, AI-powered learning experience.

The application must not be limited to ESP32. It must support multiple microcontroller development boards, starting with:

1. **ESP32 DevKit** — Wi-Fi/Bluetooth-capable microcontroller board.
2. **Arduino Uno R3** — beginner-friendly ATmega328P-based development board.

Design the application architecture so additional boards can be introduced later without rewriting the entire application.

Students should be able to select a microcontroller board, choose a lesson, drag and drop components into a virtual workspace, connect component pins, receive AI-powered explanations, generate board-compatible code, validate circuit connections and simulate supported behavior directly in the browser.

The application must function as an interactive electronics tutor rather than a static tutorial website or a standalone chatbot.

## 2. Technology Stack

### Frontend
- HTML5
- CSS3
- Vanilla JavaScript
- SVG or HTML5 Canvas for the interactive circuit builder
- Responsive layout suitable for desktop and laptop screens
- No frontend framework is required

### Backend
- Node.js
- Express.js
- REST API endpoints
- dotenv for environment variables
- Backend-side request validation and error handling

### AI Integration
- Use the authorized AI API provided for the bootcamp.
- All AI requests must pass through the Node.js backend.
- Store API credentials in backend environment variables.
- Never expose API keys in browser code, frontend configuration, logs or public repositories.
- Do not download or host the complete AI model locally.
- Keep the AI provider integration in a separate service module.
- Do not assume a specific AI provider unless its details are supplied.

### Simulation
- Build a lightweight JavaScript simulation engine.
- Implement deterministic validation rules for supported boards and circuits.
- Simulate supported digital inputs and outputs in the browser.
- Clearly distinguish simulated behavior from physical hardware execution.
- Do not use eval() or unrestricted dynamic code execution for AI-generated programs.
- Do not claim to compile or execute arbitrary microcontroller firmware.

### Storage
A database is optional for the first prototype. Keep circuits, component positions and simulation state in browser memory. Add persistent storage only if required later.

## 5. Initial Learning Lessons

Implement three lessons for the first version.

### Lesson 1: LED Blinking

Supported boards:
- Arduino Uno R3.
- ESP32 DevKit.

Components:
- Selected microcontroller board.
- LED.
- Current-limiting resistor.
- Connecting wires.

Workflow:
1. Select a board.
2. Choose the LED blinking lesson.
3. Learn about GPIO pins, LEDs, resistors and ground.
4. Drag components into the workspace.
5. Connect the GPIO, resistor, LED and ground.
6. Validate the circuit using board-specific rules.
7. Ask the AI assistant for explanations.
8. Generate code for the selected board.
9. Simulate the blinking LED.
10. Change the supported blink interval and observe the output.

For Arduino Uno R3, an example GPIO is D8. For a compatible ESP32 DevKit, GPIO2 may be used as an example if supported by the specific board configuration.

These are example configurations, not universal pin assignments. The application must generate code using the actual selected GPIO.

Example Arduino Uno-style code:

```cpp
const int LED_PIN = 8;

void setup() {
  pinMode(LED_PIN, OUTPUT);
}

void loop() {
  digitalWrite(LED_PIN, HIGH);
  delay(500);

  digitalWrite(LED_PIN, LOW);
  delay(500);
}
```

The code generator should adapt the pin configuration for the selected board.

## 6. Circuit Data Model

Use a common data model for all boards and lessons.

Example:

```js
const circuit = {
  board: "arduino-uno-r3",
  lesson: "led",

  components: [
    {
      id: "board-1",
      type: "arduino-uno-r3",
      x: 80,
      y: 100
    },
    {
      id: "led-1",
      type: "led",
      x: 320,
      y: 120
    },
    {
      id: "resistor-1",
      type: "resistor",
      x: 240,
      y: 120,
      resistance: 220
    }
  ],

  connections: [
    {
      from: "board-1.D8",
      to: "resistor-1.pin1"
    },
    {
      from: "resistor-1.pin2",
      to: "led-1.anode"
    },
    {
      from: "led-1.cathode",
      to: "board-1.GND"
    }
  ]
};
```

This is an example data structure, not an automatic declaration that the circuit is valid.

The circuit validator must verify pin availability, component polarity, current-limiting resistance, ground return, supported voltage levels and board-specific rules.

Keep board configuration separate from component rendering and simulation logic.

## 7. Circuit Validation

Implement deterministic JavaScript validation.

For every circuit:
- Verify the selected board is configured.
- Verify required components are present.
- Verify connected pins exist on the selected board.
- Check that connections use compatible pin types.
- Check lesson-specific wiring rules.
- Check LED polarity and current-limiting resistance.
- Check ground and power connections.
- Check that the generated program uses the configured pins.
- Reject unsupported connections and board configurations.

For push buttons:
- Verify the input pin is supported.
- Verify the required pull-up or pull-down arrangement.
- Verify the LED output circuit.

For DHT11:
- Verify power, ground and data connections.
- Verify the data pin and voltage requirements for the selected configuration.

Return meaningful errors and warnings. AI can explain these errors, but the deterministic validator must determine whether a circuit passes.

## 8. Simulation Engine

Implement a lightweight custom JavaScript simulator.

### LED
- Simulate HIGH and LOW output states.
- Animate blinking using the supported program configuration.
- Use the selected board's configured pins.
- Stop timers when the simulation stops, resets or changes lessons.

### Push Button
- Provide a clickable virtual button.
- Update the simulated digital input.
- Apply the defined lesson logic to control the LED.

### DHT11
- Display simulated temperature and humidity.
- Allow sample values to be changed within defined ranges.
- Update the output panel.
- Clearly mark readings as simulated.

### Code compatibility

For the initial prototype, support a small documented subset of Arduino-style operations, such as pinMode(), digitalWrite() and delay() for the LED lesson.

Use a safe parser or validated structured program representation. Do not execute arbitrary generated code.

If code contains unsupported instructions, explain that the current simulator cannot run them instead of pretending that execution succeeded.

Do not describe the application as a complete electrical simulator, compiler or firmware emulator.

## 15. AI API Key Usage Dashboard

### Objective

Add an **AI API Key Usage** item to the Microcontroller AI Lab interface. When the owner clicks it, open a dashboard showing usage information for the **specific AI API key configured for this application in the backend environment variables**.

This dashboard is for monitoring the configured API key, not for combining usage from unrelated API keys or displaying general application analytics.

### A. Usage Source and Accuracy

- Use the AI provider's official usage or billing API if it supports usage information for the configured API key or the account/project associated with that key.
- Use the same provider configuration and credentials that the application uses for AI requests. Do not request the API key from the frontend.
- If the provider does not expose usage scoped to an individual API key, clearly explain this limitation. In that case, track requests made by this application using the configured key and label the figures **Application-tracked usage for this configured key**. Do not claim that these figures include usage from other applications using the same key.
- Never invent token counts, costs, quotas, limits, or billing details.
- If the provider's usage API is unavailable or the configured provider does not support the requested metric, show **Unavailable from provider** and explain what can be tracked locally.
- Keep provider-specific usage retrieval in a separate backend service module. Do not assume all AI providers expose the same usage endpoints or response fields.

### B. Dashboard Interface

Add an **AI API Key Usage** navigation item to the application. Clicking it opens a dedicated dashboard with a Back to Lab control.

Show these metrics when the provider supplies them:
1. Total input/prompt tokens.
2. Total output/completion tokens.
3. Total tokens.
4. Number of API requests.
5. Successful and failed requests, where available.
6. Model name(s) associated with the configured key.
7. Usage period and last-updated timestamp.
8. Estimated cost or provider-reported cost, only when available and clearly identified.

Display the configured key using a safe label such as `Configured API key` or a masked suffix if the application can obtain that suffix safely. **Never display the complete API key.** Do not send the key to the frontend.

### C. Filters and Usage Details

Where the provider's API supports these dimensions, allow the owner to filter usage by:
- Today.
- Last 7 days.
- Last 30 days.
- A custom date range.
- Model.

Show a detailed table with available fields such as timestamp or reporting period, model, input tokens, output tokens, total tokens, request count and cost. Do not promise per-request details if the provider only returns aggregated usage.

Clearly distinguish:
- **Provider-reported key/account usage:** usage retrieved from the official provider API. If the provider reports account/project-level rather than key-level usage, label it accurately.
- **Application-tracked usage:** requests recorded by this Microcontroller AI Lab backend while using its configured key.

Do not combine these two sources into one total unless the calculation is valid and the dashboard explains the scope.

### D. Backend Requirements

Implement suitable endpoints, adapting them to the selected AI provider:
- `GET /api/usage/summary` — return usage summary for the configured provider/key scope.
- `GET /api/usage/details` — return detailed or time-bucketed usage when supported.
- `GET /api/usage/status` — report whether provider usage retrieval is configured and available.

The backend must:
- Read credentials from environment variables.
- Call only documented provider usage endpoints.
- Validate date filters and other query parameters.
- Handle missing permissions, unsupported endpoints, rate limits, timeouts and provider errors.
- Keep provider credentials and authorization headers out of API responses and logs.
- Protect usage endpoints from unauthorized access. For a local bootcamp prototype, restrict access to local development and document that authentication/access control is required before public deployment.

If the provider does not offer key-scoped usage data, optionally maintain local records of the AI requests made by this application. Record only metadata needed for usage tracking, such as timestamp, model, feature, token counts returned by the AI response, status and duration.
